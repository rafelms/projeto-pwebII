# 📋 Relatório de Implementação: Herança com JPA

Este relatório documenta as alterações feitas no projeto para atender aos requisitos da atividade de **Mapeamento com Herança JPA**.

A estratégia de herança escolhida foi a **`JOINED` (Uma tabela para cada classe da hierarquia)**, pois ela favorece a normalização do banco de dados, não deixando colunas vazias (nulas) como aconteceria na estratégia `SINGLE_TABLE`.

---

## ✅ 1. Checklist de Requisitos Atendidos

- [x] **`Pessoa` definida como superclasse:** Criada classe abstrata `Pessoa` contendo `id`, `email` e `telefone`.
- [x] **`PessoaFisica` e `PessoaJuridica`:** Criadas herdando de `Pessoa`.
- [x] **Adaptação de `Paciente` e `Medico`:** Ambas foram refatoradas para `extends PessoaFisica`.
- [x] **Estratégia de Herança:** Utilizada a estratégia `@Inheritance(strategy = InheritanceType.JOINED)`.
- [x] **Relacionamento mantido:** O mapeamento `@OneToMany` e `@ManyToOne` com `Consulta` continuou funcionando intacto.
- [x] **Tabelas e Views:** Formulários e listagens (Thymeleaf) foram atualizados para exibir os dados herdados (`cpf`, `email`, etc).
- [x] **`import.sql` atualizado:** Scripts de inserção refeitos para popular os dados respeitando as múltiplas tabelas geradas pela herança.

## 🔍 2. O que notar e comentar nos LOGS (Destaque para a avaliação)

O professor informou que vai analisar os **logs de criação do JPA**. Como escolhemos a estratégia **`JOINED`**, o Hibernate faz um trabalho muito específico que você deve apontar durante a avaliação:

### Destaque A: A Criação de Múltiplas Tabelas
Na estratégia `JOINED`, **cada classe da hierarquia vira uma tabela própria**. Nos logs de inicialização (`spring.jpa.show-sql=true`), você notará:

```sql
Hibernate: create table pessoa (id bigint generated by default as identity, email varchar(255), telefone varchar(255), primary key (id))
Hibernate: create table pessoa_fisica (id bigint not null, cpf varchar(255), nome varchar(255), primary key (id))
Hibernate: create table paciente (id bigint not null, primary key (id))
Hibernate: create table medico (crm varchar(255), id bigint not null, primary key (id))
```
🗣️ **Como comentar com o professor:**
> *"Professor, note nos logs que o Hibernate criou uma tabela para cada classe. A tabela `pessoa` tem o gerador de ID (auto-incremento), mas as tabelas filhas como `pessoa_fisica` e `paciente` **não geram ID próprio**. O ID delas é apenas `bigint not null`, pois elas reaproveitam o ID gerado na superclasse."*

### Destaque B: O papel do `@PrimaryKeyJoinColumn` nas Foreign Keys
Nos logs, logo após criar as tabelas, o Hibernate amarra a herança usando **Chaves Estrangeiras (Foreign Keys - FK)** ligando as chaves primárias (PK):

```sql
Hibernate: alter table if exists pessoa_fisica add constraint FK... foreign key (id) references pessoa
Hibernate: alter table if exists paciente add constraint FK... foreign key (id) references pessoa_fisica
Hibernate: alter table if exists medico add constraint FK... foreign key (id) references pessoa_fisica
```
🗣️ **Como comentar com o professor:**
> *"Aqui está a mágica da estratégia JOINED, professor. Nos logs das Constraints, podemos ver que a coluna `id` da tabela `paciente` é, ao mesmo tempo, a **Chave Primária (PK)** daquela tabela e uma **Chave Estrangeira (FK)** apontando para a tabela `pessoa_fisica`. Foi a anotação `@PrimaryKeyJoinColumn(name = "id")` que garantiu esse mapeamento relacional de herança perfeito."*

### Destaque C: Os Inserts no `import.sql`
Se o professor abrir seu `import.sql`, mostre a ele que para inserir **UM único paciente**, foi preciso fazer **TRÊS inserts**:

```sql
INSERT INTO pessoa (id, email, telefone) VALUES (1, 'joao.silva@email.com', '(11) 99999-1111');
INSERT INTO pessoa_fisica (id, nome, cpf) VALUES (1, 'João Silva', '111.222.333-44');
INSERT INTO paciente (id) VALUES (1);
```
🗣️ **Como comentar com o professor:**
> *"Como os dados estão normalizados em tabelas separadas pela hierarquia JOINED, para criar um Paciente no SQL eu precisei popular a base (Pessoa), a classe intermediária (PessoaFisica) e finalmente a classe concreta (Paciente), sempre utilizando o mesmo ID para que o JPA consiga fazer o `JOIN` na hora de buscar os dados."*

## 💻 3. Pontos Chave no Código-Fonte

Caso ele peça para ver o código Java, abra as seguintes classes e destaque:

1. **`Pessoa.java`**:
    - Destaque a anotação: `@Inheritance(strategy = InheritanceType.JOINED)`
    - Comente que ela é abstrata (`public abstract class Pessoa`), pois não faz sentido instanciar uma "Pessoa" genérica no sistema, apenas instâncias concretas (Paciente, Médico, etc).

2. **`PessoaFisica.java` e subclasses**:
    - Mostre o uso da herança nativa do Java (`extends Pessoa`).
    - Mostre a anotação `@PrimaryKeyJoinColumn(name = "id")`, explicando que é ela quem ensina ao JPA como juntar (JOIN) essa tabela com a tabela pai.

3. **`Paciente.java` / `Medico.java`**:
    - Mostre que todos os campos repetidos (nome, telefone) foram apagados dessas classes, comprovando o **baixo acoplamento** e o forte reuso de código proporcionado pela herança e pela OO (Orientação a Objetos).
